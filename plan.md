## 0. Instructions to implementation agents

**Read this document in full before planning or changing code.** Treat it as the project's controlling requirements document. Implementation details may evolve, but do not silently weaken the educational constraints, data-leakage controls, verification requirements, or separation between neural inference and deterministic validation.

1. **Work in small, reviewable increments.** Make each lesson and each milestone executable and independently testable. Keep working code on the default branch; use short-lived topic branches or separate worktrees for concurrent agents.
2. **Build, do not import, the model.** Use PyTorch tensors, autograd, optimizers, and optional low-level kernels; do not load pretrained weights, call commercial language-model APIs, or wrap an existing Transformer-model implementation as the core model.
3. **Preserve one implementation of each concept.** Notebooks explain and invoke tested source modules; they must not become divergent copies of production code. Small pedagogical snippets are permitted when explicitly labeled.
4. **Prove correctness before scaling training.** First pass unit tests, causality and gradient checks, and a one-batch overfit test. Expensive training is a separately authorized, bounded experiment.
5. **Never present desired examples as actual model output.** All reported results must be generated by a recorded checkpoint and reproducible evaluation command. Report failed runs and negative results.
6. **Treat generated interpretations as untrusted proposals.** JSON parsing, schema validation, identity resolution, and later SHACL validation must be independent of the neural network. No text may trigger real project changes automatically.
7. **Maintain implementation evidence.** Each milestone includes code, tests, tutorial explanations, reproducible commands, an evidence report, known limitations, and a review checklist.
8. **Escalate material scope or architectural changes to a human maintainer.** Agents may propose amendments to this plan or an Architecture Decision Record (ADR), but must not approve their own changes to the research hypotheses, frozen evaluation sets, or validation trust boundary.
9. **Do not imply commands already work.** CLI commands and files specified below are acceptance contracts to implement, not claims about the current repository.

### Definition of “from scratch”

The tokenizer, probability model, attention mechanism, Transformer blocks, training-data generator, loss masking, decoder, and evaluation logic are implemented in this repository using fundamental PyTorch operations. PyTorch's automatic differentiation and standard numeric primitives are explicitly allowed. An optional optimized attention backend may be added *after* verifying equivalence to the transparent reference implementation. There is no pretrained foundation model, tokenizer vocabulary trained by another provider, downloaded model checkpoint, hidden service, or external LLM at runtime or in the core dataset-production path.

## 1. Executive summary

### The idea

Build a tiny but authentic **decoder-only, causal Transformer**—a miniature GPT-style language model—from randomly initialized weights. Present its construction as a sequence of follow-along, executable lessons. In the final core exercise, train it to interpret natural-language resource-allocation instructions and questions into canonical JSON.

The example domain is deliberately narrow: projects, people, hours, and calendar weeks. A participant should be able to type:

```text
Assign Ingrid to project Coral for 12 hours in week 42.
```

and aim to obtain:

```json
{"intent":"allocate","person":"Ingrid","project":"Coral","hours":12,"week":42}
```

A paraphrase such as “Book twelve hours of Ingrid's time for Coral in week 42” should ideally yield the same interpretation. A question such as “Who is working on Coral in week 42?” should yield a different intent:

```json
{"intent":"query_allocations","project":"Coral","week":42}
```

These are **target behaviors**, not claims about model performance. The model must learn token prediction from examples. A held-out benchmark must determine whether it generalizes beyond memorized sentences and templates.

### Central thesis

A small causal Transformer can be an effective teaching tool for demonstrating the mechanics of modern language modeling, and a useful experiment in whether carefully restricted language-to-structure mapping can be learned with fewer than roughly one million parameters. The project does **not** claim general language understanding, reliable open-domain interpretation, or reasoning comparable to a large language model.

### Two deliberately separate outcomes

- **Core deliverable (mandatory):** a runnable, fully documented tiny GPT-style model and an evaluated, narrowly scoped natural-language-to-JSON interpreter.
- **Semantic extension (later, optional):** deterministic conversion of validated interpretations to an ontology-backed RDF knowledge graph, followed by SHACL validation, traceable queries, and a small neurosymbolic demonstration.

### Why this is pedagogically useful

Participants will observe the transition from simple bigram probabilities to embeddings, self-attention, Transformer blocks, cross-entropy training, and autoregressive decoding. They will then see the distinction between minimizing training loss and learning reusable linguistic patterns. The knowledge-graph extension illustrates why neural interpretation and symbolic constraint checking are complementary, not interchangeable.

### Evidence and cautions

- The Transformer architecture originates in *Attention Is All You Need* (Vaswani et al., 2017).
- *TinyStories* (Eldan and Li, 2023) demonstrates coherent generation with language models substantially smaller than common commercial LLMs when training data is strongly constrained. It does **not** establish the specific accuracy of the interpreter proposed here.
- Synthetic text-to-JSON supervision is **not equivalent** to broad natural-language pretraining. This project should describe its later stage accurately as domain-specific conditional autoregressive training from random initialization; optional preliminary corpus pretraining is a separately measured experiment.

References are collected in §19.

## 2. Goals, hypotheses, and boundaries

### 2.1 Functional and educational goals

1. Explain tokenization, probability, cross-entropy, gradients, embeddings, attention, causal masking, residual connections, and autoregressive generation in a sequence a beginner can follow.
2. Implement a GPT-like decoder-only model without importing pretrained model code.
3. Support a CPU-only smoke-test path and an explicitly configured GPU training path.
4. Train from scratch on a small, generated, versioned domain dataset.
5. Expose a CLI and optional local web demo that show the raw output, parsed interpretation, validation status, and an honest indication of uncertainty or failure.
6. Evaluate in-distribution examples, unseen combinations, withheld paraphrase families, and out-of-scope or ambiguous inputs.
7. Include a transparent non-neural baseline, ablations, training curves, selected attention visualizations, and machine-readable evaluation reports.
8. Make the work directly usable as a reproducible workshop or self-guided tutorial.

### 2.2 Testable hypotheses

- **H1 (learning):** A tiny Transformer trained from random initialization can outperform an untrained model and an appropriate trivial statistical baseline on the scoped text-to-JSON task.
- **H2 (generalization):** Given carefully diversified training data, it can achieve nonzero and measurably useful generalization on intentionally withheld slot combinations and some unseen wording families.
- **H3 (model contribution):** On at least one sufficiently challenging held-out subset, the Transformer improves over a transparent rules/templates baseline. If it does not, the result is reported as a limitation rather than concealed.
- **H4 (extension):** A deterministic ontology-mapping/SHACL pipeline can increase structural consistency, traceability, and safe rejection of invalid results without falsely presenting validation as proof of correct linguistic interpretation.

### 2.3 Out of scope for version 1

General chat, broad multilingual ability, open-world factual question answering, retrieval-augmented generation, a production project management system, writing to a real database, distributed training, custom GPU kernels, sophisticated tokenization research, arbitrary SQL/SPARQL authored by the model, and guarantees of semantic correctness.

No hidden calls to external LLMs and no fallback to regular expressions in the **model output path**. Deterministic preprocessing, schema checks, and ontology mapping are allowed, but must be clearly identified and evaluated separately. A regex/rules interpreter may exist only as an explicitly labeled comparison baseline.

### 2.4 Success tiers

- **Minimum educational success:** all eight lessons run, the model has working forward/backward passes and generates tokens from learned weights, and the complete training/evaluation pipeline is reproducible—even if semantic performance is modest.
- **Target practical demonstration:** a trained checkpoint produces valid JSON and meaningful correct interpretations for a useful proportion of held-out, in-domain instructions; published reports distinguish easy and difficult cases.
- **Stretch research success:** the Transformer beats the rules/template baseline on a preregistered generalization test and safely rejects a reasonable fraction of unsupported requests without excessive false acceptance.

Do not redefine these tiers after looking at the locked test set.

## 3. Reference architecture

```text
                         EDUCATIONAL PATH
    input text
        │
        ▼
  byte tokenizer ──► token + learned positional embeddings
                               │
                               ▼
                 [pre-LN causal attention + residual]
                 [pre-LN feed-forward   + residual]  × N
                               │
                               ▼
                  final norm + LM vocabulary head
                               │
                    autoregressive decoding
                               │
                    generated UTF-8/JSON text
                               │
                               ▼
                    strict JSON/schema checks
                               │
                    untrusted interpretation

                         OPTIONAL EXTENSION
                               │
                   entity / identity resolution
                               │
                     canonical semantic mapping
                               │
                     RDF staging graph + SHACL
                               │
                      approved local graph/query
```

### 3.1 Reference model profile

| Parameter | `tiny` reference configuration | `cpu-smoke` configuration |
|---|---|---|
| Layers | 4 | 2 |
| Attention heads | 4 | 4 |
| Embedding width (`d_model`) | 128 | 64 |
| Feed-forward width | 512 | 256 |
| Maximum context | 512 byte/special tokens | 256 byte/special tokens |
| Vocabulary | 256 raw byte IDs + 4 special IDs = 260 | Same |
| Position mechanism | Learned absolute positions | Same |
| Block structure | Pre-LayerNorm, causal self-attention, residual, GELU feed-forward | Same |
| LM head | Weight-tied to token embeddings | Same |
| Initial weights | Random | Random |
| Approximate parameter scale | ~0.9 million | ~0.13 million |

Parameter estimates must be verified using the implemented model's parameter counter; the estimates are not benchmark results. The four special tokens are `<pad>`, `<bos>`, `<sep>`, and `<eos>` with explicitly documented IDs. A byte tokenizer makes arbitrary UTF-8 representable without using an externally pretrained tokenizer, at the cost of longer sequences and more challenging generation of names/numbers. This trade-off is itself a useful educational topic.

If examples exceed the context budget, **reject or report them**; never silently truncate target values or prompts. Provide length histograms before finalizing the dataset. The CPU profile is primarily for correctness smoke tests, not a promise of successful semantic learning.

### 3.2 Model contracts

- `tokenize(text: str) -> list[int]` and `decode(ids: Sequence[int]) -> str` have documented UTF-8 behavior, special-token handling, and round-trip tests.
- `TinyGPT(config).forward(input_ids)` returns logits of shape `[batch, time, vocab_size]`; loss is calculated by a separately testable utility or an explicitly documented optional forward argument.
- Attention is causal: a future token cannot influence earlier-position logits in evaluation mode. A dedicated test must mutate future inputs and compare earlier logits.
- `generate(prompt_ids, max_new_tokens, strategy, seed)` samples or greedily decodes tokens one step at a time; it stops on `<eos>` or at an explicit length limit.
- The training pipeline saves model weights **and** tokenizer/config/generation metadata; the loader checks compatibility and fails closed on mismatches.
- Any attention visualization is identified as an observed weight pattern, **not** a validated explanation of the model's reasoning.

### 3.3 Training objective and masking

A conditional training sequence is:

```text
<bos>instruction text<sep>canonical JSON target<eos>
```

Train with teacher-forced causal next-token cross-entropy. The standard supervised objective should mask out losses for the instruction/prefix tokens and padding. Count loss on the target JSON tokens **and on `<eos>`**. Be explicit about shifting: logits at position *t* predict input token *t + 1*. Unit tests must verify that the first generated JSON token contributes to loss and that loss never comes from padding or prompt-only tokens. Do not unintentionally train the model to emit a copy of the whole prompt.

The lessons may also train a bigram model and a standalone general next-token model to explain pretraining. They are distinct experiments, not pretrained dependencies of the final interpreter unless an explicit ablation introduces a local, from-scratch corpus-pretraining stage.

### 3.4 Decoding and validity

Use greedy decoding as the default reproducible evaluator. Optionally expose temperature/top-k for exploration; never compare stochastic generations without recording settings and seeds. Enforce maximum generated length, strict UTF-8 decoding, strict JSON parsing, no extra prose or markdown fences, rejection of duplicate JSON keys, and schema validation. If decoding reaches a limit or a token sequence is invalid, return a structured failure state. Constrained/grammar-based decoding can be studied later, but must be measured independently and never be used to claim the unconstrained model learned valid JSON.

## 4. Narrow language-understanding task specification

### 4.1 Domain

An educational, fictitious resource-planning domain: **people**, **projects**, **weekly allocations**, and **hours**. Begin in English. Use invented names and project identifiers with clear documented catalogs. No real personal, employee, project, or internal financial data is needed.

The initial supported intent set is deliberately small:

| Intent | Required fields | Example |
|---|---|---|
| `allocate` | `person`, `project`, `hours`, `week` | “Assign Ingrid to Coral for 12 hours in week 42.” |
| `query_allocations` | `project`, `week` | “Who is working on Coral in week 42?” |
| `unsupported` | none | A clear request outside this domain |

If a request clearly belongs to an intent but lacks a mandatory value, downstream validation may return `needs_clarification` with missing fields. Do not initially require the model to reliably generate free-form clarification questions. Contradictory or underspecified inputs must never be converted into executable commands.

### 4.2 Canonical JSON schemas

The model generates **one JSON object**, not natural-language explanations. Example output shapes:

```json
{"intent":"allocate","person":"Ingrid","project":"Coral","hours":12,"week":42}
```

```json
{"intent":"query_allocations","project":"Coral","week":42}
```

```json
{"intent":"unsupported"}
```

Schema rules:

- Exact allowed keys per intent; no additional properties.
- Known categorical intent string; `person` and `project` are nonempty surface strings at this stage.
- `hours` is an integer in the demo range **1–40**; `week` is an integer in **1–53**. These limits are example-domain policy, not universal workforce rules.
- JSON serialization is canonical and documented: deterministic field order, separators, escaping, integer formatting, and UTF-8 normalization assumptions.
- The model's output is **not** an authorization or an instruction to mutate any system.
- Entity IDs are assigned only later by a separate deterministic resolver; do not force a tiny model to memorize opaque global identifiers.

A future, versioned schema may add `remove_allocation`, date ranges, percentages, budget units, and project identifiers. Do not add those during MVP without a scope-change decision.

### 4.3 Language variation and controls

Generate examples varying word order, synonymous verbs (`assign`, `book`, `schedule`, `reserve`), numeric and spelled-out hour values, pronouns only where unambiguous, optional filler, capitalization, and punctuation. Record which linguistic capabilities each template exercises. Use a **controlled, documented** normalization policy; do not create a preprocessing rule that secretly solves the task.

Negative examples should include unsupported domains, impossible values, missing required slots, negation, ambiguous entities, requests spanning several allocations, and deliberate attempts to influence output formatting. Define the correct disposition of each negative class **before** evaluating it. Values outside schema range should be rejected by validation even if the model emits a plausible object.

### 4.4 The uncertainty/abstention contract

No probability score from a one-million-parameter model should be called a calibrated confidence by default. If token log-probability or other scores are used as rejection signals, calibrate thresholds on a **validation/calibration** partition and report false-accept and false-reject rates on the locked test set. Unsupported requests, JSON failures, unknown identities, missing fields, and SHACL violations must remain visibly distinct failure types.

## 5. Synthetic dataset design and leakage prevention

### 5.1 Dataset generator

Implement a seedable, versioned grammar/template generator that produces pairs of `utterance` and canonical `target`, together with metadata:

```json
{
  "example_id": "...",
  "utterance": "Assign Ingrid to project Coral for 12 hours in week 42.",
  "target": {"intent":"allocate","person":"Ingrid","project":"Coral","hours":12,"week":42},
  "intent": "allocate",
  "template_family": "allocate_direct_v1",
  "slot_signature": ["Ingrid", "Coral", 12, 42],
  "difficulty": "basic",
  "split": "train"
}
```

Stable IDs are based on a documented canonical representation. Include generator version, seed, source template ID, and output manifest. Reject duplicate normalized utterances across splits, contradictory labels, missing required fields, and oversized sequences. Preserve provenance of manually authored examples; never claim they were independently human-validated unless they were.

### 5.2 Suggested scale (tunable, not predetermined success)

- **Smoke:** hundreds to a few thousand records, for data and model correctness only.
- **Initial train:** approximately 20,000–40,000 generated records, with a few thousand for validation and evaluation, subject to actual context-length and runtime measurements.
- **Stretch:** more diverse templates and examples only if error analysis and learning curves justify them.

Avoid a dataset consisting mostly of trivially duplicated phrasing or highly skewed numeric and entity distributions. Generate a data card documenting catalog sizes, value ranges, composition, limitations, and known bias.

### 5.3 Distinct test suites

| Suite | Purpose | Isolation rule |
|---|---|---|
| `iid` | New instances of supported templates | No identical utterance across train/validation/test |
| `combination` | Unseen people/project/number combinations | Reserve selected slot tuples; keep template families potentially shared |
| `paraphrase` | Generalize beyond familiar wording | Hold out entire phrasing/template families |
| `curated` | Manually authored sentences | Independent authoring after train generator freezes; no template reuse |
| `negative` | Unsupported, incomplete, contradictory, out-of-range and adversarial inputs | Explicit reference dispositions and rejection metrics |
| `length_unicode` | Long inputs, UTF-8, punctuation, edge bounds | Boundary values and explicit over-length rejection |

Distinct suites must not be conflated into a single impressive-looking accuracy. Freeze immutable test fixtures before model tuning; changes require a documented revision and a fresh release of the benchmark. Validation may be inspected for tuning; locked test cases must not be repeatedly used to steer implementation choices.

### 5.4 Baselines and experimental controls

1. **Untrained TinyGPT** using identical evaluation code.
2. **Bigram or token-transition baseline** to demonstrate the improvement beyond local statistics.
3. **Transparent deterministic rules/template parser**, scored on the same suites. It must be clearly marked as a baseline, not a fallback used to improve neural outputs.
4. **Optional ablations:** fewer layers, no attention / limited context, narrower embeddings, direct supervised training versus local corpus pretraining, changed dataset diversity, and alternate tokenizers. Each change gets its own checkpoint and manifest.

Resource budget is bounded per experimental run; no agent may automatically launch unlimited GPU jobs or optimize against locked tests.

## 6. Teaching curriculum and implementation milestones

The tutorial comprises eight sequential lessons. Each lesson has a short narrative, prerequisites, one runnable notebook, a tested library implementation where appropriate, formative exercises, and a milestone checklist. The implementation and teaching sequence are aligned, but coding agents may independently build datasets and infrastructure once shared contracts are agreed.

### M0 — Repository, environment, and contracts

**Build:** `pyproject.toml` or equivalent plus exact dependency lock/pins, Python version policy, `README.md`, local setup and CLI conventions, formatting/linting/type checking, `pytest`, CI smoke job, configuration system, docs templates, and runnable examples. Pin package versions only after selecting and verifying an actually installable compatible set; do not invent version compatibility.

**Acceptance:** clean install, import, lint, type checks, basic tests, and an offline CPU check work from documented commands. All code is licensed and toy data is clearly non-sensitive.

### M1 — Tokenization and probability

**Build:** byte-level tokenizer and a count-based bigram demonstration. Show vocabulary, encoded IDs, decoding, next-token counts/probabilities, and sampling. Explain byte-level advantages and sequence-length costs.

**Acceptance:** round trips over ASCII and representative Unicode, explicit behavior for malformed UTF-8, stable special IDs, deterministic sampling with seeded random state, and probability sums checked numerically.

### M2 — Trainable bigram language model

**Build:** PyTorch parameterized bigram predictor, logits/softmax, cross-entropy, gradients, minibatches, optimizer, simple train/validation plots, generated toy strings.

**Acceptance:** loss decreases on a learnable toy dataset, numerical checks where practical, a test that gradients flow, and a concise explanation of overfitting versus validation loss.

### M3 — Embeddings and first-principles attention

**Build:** token embeddings, positional embeddings, query/key/value linear layers, scaled dot-product attention, lower-triangular causal mask, an attention-weight visualization, and a miniature single-head model.

**Acceptance:** shape tests, finite forward/backward values, attention rows sum to one over allowed positions in evaluation mode, future-mask weights are zero, earlier-position logits are invariant to later input changes in evaluation mode, and a manual tiny example agrees with a separately constructed reference calculation.

### M4 — GPT-style decoder

**Build:** multi-head attention, pre-LayerNorm, residual pathways, GELU feed-forward MLP, stacked blocks, final normalization, tied LM head, initialization, parameter counter, autoregressive decoder, checkpoint save/load.

**Acceptance:** forward/backward smoke tests, causality invariance across full stack, correct maximum-context behavior, save/reload logits equivalence in eval mode, one-batch overfit, bounded generation and EOS stopping. No semantic-performance claims yet.

### M5 — Domain dataset and supervised training

**Build:** grammar and canonical-output generator, data cards, split logic, length analysis, conditional sequence packing, shifted output-only loss masks, reproducible train loop, validation and bounded checkpoint selection, experiment manifests.

**Acceptance:** split leakage tests, schema-valid targets, controlled template-family separation, masking unit tests, fixed-seed smoke run, a logged CPU training smoke run, and an explicitly configured longer training profile. Training must save loss curves and selected generated examples **clearly tagged by checkpoint and split**.

### M6 — Real evaluation and model review

**Build:** test harness for exact JSON semantic match, per-intent accuracy, per-field accuracy/F1 where applicable, valid JSON rate, coverage/rejection, OOD false acceptance, error taxonomy, latency/throughput, baselines and limited ablations.

**Acceptance:** a reproducible `evaluate` command emits JSON and Markdown reports with dataset fingerprint, checkpoint ID, configuration, commit, seed, hardware, metric denominators and confusion/error examples. Results are compared with baselines, not selected cherry-picked utterances.

### M7 — Interactive tutorial and local demo

**Build:** documented CLI and a minimal optional local UI. Input text, show raw decoded tokens, canonical parsed result, schema status, known failure reason, and optional attention/next-token probabilities. Provide an offline interactive workshop path, including a pre-trained-**by-this-project** checkpoint created by the documented training process.

**Acceptance:** a first-time user can follow the eight notebooks and run a clearly labeled example checkpoint; the UI cannot perform external side effects or silently turn malformed output into a successful interpretation. Every screenshot or sample transcript comes from an actual run and identifies the checkpoint.

### M8 — Semantic extension (separate release gate)

**Build:** an ontology, deterministic entity catalog and resolver, mapping from validated JSON to RDF staging graph, SHACL shapes, provenance, approval-free *read-only/local* graph demo, and SPARQL-based queries.

**Acceptance:** positive and negative RDF fixtures; exact expected triples; entity-resolution collisions and unknowns rejected; SHACL failures block staging-to-graph publication; independent evaluation of linguistic correctness and structural validity; provenance points to input and model version. See §13.

## 7. Evaluation methodology and decision criteria

### 7.1 Metrics

- **Loss / perplexity:** describe next-token modeling only; never substitute them for semantic success.
- **Valid JSON:** percentage with a single well-formed JSON object and no trailing content, given strict decoding.
- **Schema-valid JSON:** percentage conforming to the versioned intent schema.
- **Exact semantic match:** canonical JSON-equivalent object matches reference, including all required slots and numeric values.
- **Intent accuracy / per-field precision, recall, F1:** report by intent and individual slot, on examples where that measure is defined.
- **Generalization gap:** compare `iid`, `combination`, `paraphrase`, and `curated` results.
- **Abstention:** accepted coverage, correctness among accepted, false-accept rate for unsupported inputs, and false-reject rate on supported inputs.
- **Cost:** parameter count, training steps/tokens, device, elapsed runtime, peak memory where feasible, and tokens generated per second.

Metrics must specify whether malformed outputs count as incorrect (yes for exact match) and whether the correct target is `unsupported`. All reported percentages include sample counts, uncertainty intervals where worthwhile, and example failures.

### 7.2 Provisional demonstration targets

These are **aspirational engineering targets to be tested**, not promises of what the selected tiny model can accomplish:

| Measure | Initial target | Interpretation |
|---|---:|---|
| In-domain schema-valid JSON | ≥95% | Output formatting is mostly learned |
| `iid` exact match | ≥90% | Basic task has been learned |
| Held-out `combination` exact match | ≥80% | Some compositional generalization |
| Held-out `paraphrase` exact match | ≥70% | Generalization beyond seen grammar families |
| Unsupported false acceptance | ≤10% | Rejection behavior worth demonstrating |

Choose any final pass criteria *before* test evaluation and document their rationale. Targets are not scientific thresholds; smaller models and byte tokenization may underperform. If results fall short, publish the gap, run permitted validation-only diagnostics, and seek maintainer approval before materially changing the architecture or resetting the benchmark. Do not tweak examples post hoc to manufacture a success story.

### 7.3 Must-pass correctness tests (irrespective of metrics)

1. Tokenizer round-trip, special-token handling, and Unicode edge cases.
2. Causal invariant: changing future token IDs never changes earlier outputs in eval mode.
3. Training mask invariant: prefix/padding tokens contribute zero loss; first target and EOS contribute loss.
4. Single-batch overfit demonstrates usable gradients and capacity.
5. Checkpoint reload yields equivalent logits on the same platform and configuration.
6. Invalid UTF-8, malformed JSON, missing fields, duplicate keys, unknown intent, and over-length input produce explicit failure responses.
7. Dataset builder has no normalized utterance duplicates across splits or held-out template-family leakage.
8. Evaluator reports identical metrics on repeated evaluation of the same checkpoint/split/decoding config on a fixed platform; exceptions are documented.
9. No hidden API/model use, no model-based benchmark labeling, and no benchmark fixture mutations after freeze.

Full bit-for-bit reproducibility across different devices and PyTorch backends cannot be guaranteed. Record seeds, deterministic settings, relevant framework versions, and known remaining sources of nondeterminism, consistent with PyTorch reproducibility guidance.

### 8.1 Proposed CLI acceptance contract

The agents implement and document command equivalents to:

```bash
python -m tinygpt tokenize "Assign Ingrid to Coral"
python -m tinygpt generate-data --config configs/tiny.yaml
python -m tinygpt train --config configs/cpu-smoke.yaml
python -m tinygpt train --config configs/tiny.yaml
python -m tinygpt evaluate --checkpoint artifacts/<run-id>/model.pt --suite all
python -m tinygpt interpret --checkpoint artifacts/<run-id>/model.pt --text "Assign Ingrid to Coral for 12 hours in week 42."
```

`<run-id>` is a placeholder, not a literal existing file. Exact CLI grammar must be documented and smoke tested; avoid implementing a complex server before a working CLI. Commands must return meaningful nonzero exit codes when configurations, checkpoints, or interpretations are invalid.

### 8.2 Experiment manifests and artifacts

Each run directory contains at minimum:

```text
artifacts/<run-id>/
  config.resolved.yaml
  run.json             # timestamp, commit, environment, dataset hash, seed
  model.pt             # weights and compatible metadata
  train.jsonl          # stepwise loss and run diagnostics
  evaluation.json      # when evaluated
  evaluation.md        # when evaluated
```

Prefer safe serialization practices, document that PyTorch pickle-based checkpoint loading can be dangerous with untrusted files, and avoid loading arbitrary third-party checkpoints. Each report identifies whether data and weights are reconstructed or distributed. Model weights may be committed separately as small release assets, with checksums, licenses, and provenance; do not bloat the Git history.

## 9. Implementation quality and engineering standards

- Target a supported, pinned Python/PyTorch toolchain; ensure dependencies actually resolve together. Use one lockfile and a documented reproducible environment creation process.
- Type annotate public functions; avoid unnecessary abstractions and implicit mutable global state. Data schemas and model configs must be versioned.
- Keep the educational attention implementation readable even if a faster path is added later. If using `torch.nn.functional.scaled_dot_product_attention`, verify causal-mask conventions and dropout semantics against the framework documentation and compare numerical behavior on small cases.
- Ensure train/eval mode differences are covered by tests. Seed Python, NumPy if used, and PyTorch; document limits of deterministic execution.
- Use train-only loss masking in code with explicit test assertions; use numerical stability safeguards around logits and softmax.
- Avoid mixed-precision and compilation as default educational requirements; add them only behind opt-in configuration with correctness tests.
- Run short CPU tests in CI; long training belongs to explicit benchmark jobs, not every pull request.
- Cache datasets with manifest-based invalidation and no silent regeneration. Honor a maximum-step, max-token, and checkpoint budget.
- No personal/secret data, network services, or cloud credentials are needed for the core project. Keep the demo local and offline by default.
- Every error path should be explicit and legible to learners. No broad exception handlers that hide failures or convert arbitrary text into an apparently valid response.
- A failing correctness gate cannot be waived by a high accuracy score.

## 12. Learner experience and demonstration design

The educational narrative should repeatedly show **input → representation → prediction → measured behavior**, with visualizations that expose rather than conceal the mechanism.

**Core demonstrations:**

- Token IDs and byte sequence length for the same sentence.
- Bigram next-token probability table and sampled sequences.
- Loss curves for training versus validation; model behavior before/after training.
- Attention matrix with causal upper triangle masked; optional selected attention head/layer.
- Next-token distribution and one-token-at-a-time JSON generation.
- Live test of familiar, unseen-combination, held-out paraphrase, and unsupported examples.
- Comparison between neural output, deterministic baseline, strict schema check, and eventual KG validator.
- Interactive error gallery showing malformed JSON, swapped slots, numerals, ambiguity, and unknown entities.

**Workshop UX:** each lesson begins with a two-minute conceptual explanation, contains small code cells and inspectable tensor shapes, and ends with one experiment plus a short “what was learned / what remains unsolved” reflection. Training results and checkpoints should be provided for participants without a GPU, but participants must also be able to create a small smoke checkpoint themselves.

**UI truthfulness:** never claim the model “understands” every sentence; show `accepted`, `invalid_output`, `schema_rejected`, `unknown_entity`, `needs_clarification`, or `unsupported`, as applicable. Display the raw model string alongside the validated interpretation in an expandable section. Do not imply that attention scores prove reasoning.

## 13. Future extension: text → knowledge graph (M8)

### 13.1 Purpose and trust boundary

Illustrate a tiny **neurosymbolic pipeline**: a trained neural model maps an utterance to a candidate intent with slots; deterministic code resolves known entities, constructs RDF triples, checks constraints, and serves safe local graph queries. **Structural validation does not prove the text was interpreted correctly.** Correctness against a reference interpretation is measured separately.

The first demonstration is read-only or writes only to a disposable, local graph created from toy data. No graph mutation is committed solely on the authority of a generated string. An optional “apply” step requires explicit user approval of the canonical resolved proposal and successful checks.

### 13.2 Proposed RDF vocabulary

The toy ontology is versioned in `ontology/planning.ttl` and uses an example namespace such as `https://example.org/tinygpt/planning#` (illustrative; not a deployed service). Keep it intentionally small:

**Classes:** `Person`, `Project`, `Allocation`, `SourceUtterance`, `Interpretation`.

**Properties:** `assignedPerson`, `assignedProject`, `hours`, `week`, `source`, `generatedByModel` or appropriately modeled PROV relations. Explicitly distinguish a proposed allocation from a real/approved allocation; avoid silently asserting unverified facts about the world.

**Constraints:** each `Allocation` has exactly one known person, one known project, one positive integer hour count in the configured demo range, and one valid week integer. Requirements involving combinations, cross-record totals, authorization, and domain-specific conflicts may need application logic or SPARQL constraints beyond basic SHACL shapes.

### 13.3 Pipeline contract

```text
user utterance
   ↓
TinyGPT-generated JSON candidate
   ↓
strict parser + JSON schema + completeness checks
   ↓
deterministic entity resolver (catalog IDs / aliases; no guessing)
   ↓
canonical proposed action / semantic intermediate representation
   ↓
RDF staging graph with source + model/checkpoint provenance
   ↓
SHACL validation and business-rule checks
   ↓
preview / human approval (if mutation requested)
   ↓
local toy graph and safe parameterized query layer
```

No model-generated SPARQL, URI, or graph write is directly executed. The model must not create authoritative person/project IDs. Identity ambiguity, duplicate aliases, and unknown entities must be shown as resolution failures. Use `rdflib` for RDF construction and `pyshacl` for SHACL validation, verifying compatible versions during the extension phase.

### 13.4 Semantic example

Candidate sentence and neural target:

```text
Assign Ingrid to project Coral for 12 hours in week 42.
{"intent":"allocate","person":"Ingrid","project":"Coral","hours":12,"week":42}
```

After deterministic resolution of `Ingrid` and `Coral` to **catalog entities**, construct a **proposed** `Allocation` node linked to those entity URIs, with integer-typed week/hours and a source utterance record. SHACL checks shape and datatype constraints. A separate query displays what the proposed allocation would mean, or reads existing approved allocations for a `query_allocations` intent. No names, assignments, or facts are created in the graph without the defined validation and approval policy.

### 13.5 Provenance and validation evidence

Record the immutable original utterance, input identifier, timestamp when available, candidate model output, model checkpoint checksum, dataset/schema/ontology versions, resolver catalog version, SHACL result, and any user acceptance action. Distinguish **model proposal**, **validated proposal**, and **approved/persisted fact** in identifiers and audit events. Use a named graph or explicit status property to avoid conflating a proposal with an asserted fact.

For queries, use approved templates/parameterization, not arbitrarily generated SPARQL. Display graph triples and the validation report to teach the division of labor. Avoid exposing sensitive data: this project uses fictional fixtures only.

### 13.6 Semantic extension acceptance tests

1. Canonical JSON → exact expected triples, independent of model accuracy.
2. Unknown/ambiguous person or project never produces a silently fabricated identity.
3. Bad datatypes, missing properties, out-of-range weeks/hours and wrong predicates cause validation failures.
4. A failed SHACL or business-rule check prevents any approved graph mutation.
5. Candidate results and approved facts remain distinguishable after serialization/reload.
6. Repeated processing of one proposal follows explicit deduplication/idempotency semantics.
7. SPARQL queries are parameterized or constructed from controlled templates and return expected results on toy fixtures.
8. Two separate metrics are reported: **text interpretation accuracy** and **RDF/constraint pipeline correctness**. A high SHACL pass rate is never presented as evidence that the model understood the input.

## 14. Future research and product extensions (after M8)

Prioritize only after the base model and benchmark are sound. Every extension receives its own hypothesis, baseline, evaluation subset, and ADR where appropriate.

| Extension | Research question / value | Prerequisite |
|---|---|---|
| Larger and smaller model ablations | What scales with width, depth, heads, or context length? | M6 metrics stable |
| Alternative tokenizers | Do character, byte, or learned BPE tokens improve numeric/name copying and generalization? | Comparable held-out splits |
| Local corpus pretraining + conditional finetuning | Does genuinely separate next-token pretraining help beyond training directly on pairs? | Carefully controlled compute/data comparison |
| Expanded grammar | Can the model learn multiple actions, conjunction, negation, time ranges, and units? | MVP semantics stable |
| More robust abstention | Can calibrated rejection reduce false acceptance without excessive refusal? | Validation-only calibration |
| Norwegian instructions | What changes with morphology, UTF-8 length, and multilingual supervision? | English baseline frozen |
| Interactive attention and neuron probes | What observable circuits or token dependencies emerge? | Honest non-causal interpretation of visualizations |
| Constrained decoding | Does grammar-constrained generation improve syntactic validity, separately from semantic accuracy? | Unconstrained baseline |
| Ontology-aware supervision | Does exposure to ontology terms improve valid concept/relationship mapping? | M8 deterministic mapping |
| More expressive KG queries | Extend from fixed intents to a safe intermediate query language | Controlled query policy |
| Incremental graph evolution | Model proposed add/update/retract actions with provenance and human approval | Versioning and audit design |
| Knowledge-led correction | Can validators return structured repair feedback without hiding original errors? | Separate raw and repaired scores |
| Confidence/error localization | Which slots or constructions most often fail, and how can they be detected? | Per-field error analysis |
| Teaching benchmark | Does the lesson sequence improve participants' mental models of attention and language learning? | Full workshop material |

Any future use of external LLMs to generate examples or judge responses must be **explicitly separated from the from-scratch core**, with dataset provenance, cost, licensing, potential contamination, and independence of evaluation disclosed. This would be a new experimental condition, not a silent implementation shortcut.

## 15. Risk register and mitigations

| Risk | Consequence | Mitigation / owner |
|---|---|---|
| Tiny model memorizes templates | Inflated demo quality | Data/evaluation agents: held-out families, combinations, independent examples |
| Byte tokenization makes copying difficult | Wrong names/numbers and low accuracy | Model/data agents: measure token lengths, error buckets, consider tokenizer ablation later |
| Accidental attention or loss-mask leakage | Misleading metrics | Model/reviewer: causality and output-target-mask tests |
| Training cost exceeds available machine | Unfinished workshop | Training agent: CPU smoke, measured run budgets, cached local checkpoint |
| Synthetic grammar is too narrow | Fragile real-language behavior | Data agent: separate curated/paraphrase benchmark and explicit limitations |
| Reviewer tunes against test labels | Invalid generalization estimate | Orchestrator/evaluation agent: frozen benchmark, audit trail, split versioning |
| Model emits plausible invalid commands | Unsafe action or false success | Demo/semantic agent: strict parsing, schema, catalog resolution, approval boundary |
| SHACL passes wrong interpretation | False claim of understanding | Semantic/evaluation agents: independent semantic ground truth |
| Multiple agents edit shared contracts | Integration regressions | Orchestrator: explicit owners, ADRs, one integrator |
| Dependencies or saved artifacts drift | Unreproducible workshop | Infrastructure/training agents: lockfile, manifests, hashes, clean install CI |
| Documentation exaggerates evidence | Scientific and educational confusion | Reviewer: distinguish targets, actual scores, caveats and baselines |

## 17. Open decisions to settle during M0

The orchestrator proposes the following default decisions and records the final choices in `docs/decisions/`:

1. **Python and PyTorch versions** — choose a compatible actively supported combination and lock tested dependencies; do not depend on an unverified version guess.
2. **Notebook tooling** — Jupyter with headless smoke execution in CI; optional alternative notebook runner if maintainable.
3. **Canonical JSON ordering** — define exact serialization and schema files before generating data.
4. **Special token IDs** — freeze 256 byte values plus four nonoverlapping special IDs; document how they appear in human-readable dumps.
5. **Length behavior** — hard reject excessive prompt/target lengths, with a recorded histogram; choose reference context sizes based on sampled data.
6. **Training duration and compute budget** — set maximum steps, tokens, device, memory and checkpoint budget after measuring a small run. Do not assume GPU availability.
7. **Holdout construction** — commit evaluation protocol and frozen test manifests before full training; protect final tests from iterative tuning.
8. **Project packaging/license** — choose a permissive educational license and appropriate ownership/attribution after confirming available source materials.
9. **Local demo implementation** — keep CLI mandatory; optional web UI only if it does not delay core scientific reproducibility.
10. **Semantic catalog / namespace** — choose stable fictitious identifiers and a resolver policy before adding RDF mapping.

Unresolved decisions should have named owners and documented provisional defaults; they must not become an excuse to rewrite the entire architecture.

Empirical motivation for studying language modeling with very small networks and restricted corpora; not a guarantee of interpretation generalization in this project.
3. **Andrej Karpathy.** [Let's build GPT: from scratch, in code, spelled out](https://www.youtube.com/watch?v=kCc8FmEb1nY) and [build-nanogpt](https://github.com/karpathy/build-nanogpt). ## 20. Final guidance to the implementation team

This project is intended to **teach the mechanics of generative language modeling and then test a narrow, falsifiable language-understanding claim**. Preserve that distinction throughout the code, tutorials, benchmark, and demo.

A trained tiny model that fails on difficult paraphrases is still a legitimate educational result if the failure is visible and explained. A polished demo that hides fragile model behavior behind templates, silent repairs, or unreported benchmark leakage is not.

The architecture should remain simple enough for a student to understand, rigorous enough for reproducible research, and modular enough to attach a deterministic knowledge-graph pipeline without changing what the neural model is responsible for.

**Implementation may begin at M0/WP-00 after human review of this plan.**
